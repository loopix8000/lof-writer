# 파일 중심 저장·SQLite·원본 파일 동기화

> 갱신일: 2026-10-18
> 현재 구현 방향: 최신 문서만 동기화하고 수정 이력은 각 기기에서 별도로 관리한다.
> 이전에 검토한 기기 간 이력 교환·원격 증분 로그 누적 설계는 사용하지 않는다.

## 기본 원칙

- 원고의 기준은 실제 Markdown 파일과 폴더다. 다른 편집기로 조회·수정할 수 있다.
- SQLite는 색인, 마지막으로 관찰한 내용, 로컬 수정 이력, 동기화 상태를 관리한다.
- 파일과 DB가 다르면 실제 파일의 변경을 읽는다. DB의 예전 내용으로 원고를 자동 복구하지 않는다.
- SQLite DB 자체와 수정 이력은 앱 동기화에 포함하지 않는다.
- 동일 문서를 여러 기기에서 각각 수정하면 충돌 사본을 보존한다. PC 시각만 비교하여 한쪽을 버리지 않는다.

## 로컬 저장 구조

```text
서재/
├─ .lof/
│  ├─ vault.json
│  ├─ library.sqlite          # 각 기기의 관리 DB
│  ├─ library.sqlite-wal      # 실행 중 생성될 수 있음
│  ├─ library.sqlite-shm
│  ├─ library.sqlite.lock     # 같은 서재의 중복 앱 사용 방지
│  ├─ migrations/sqlite-v1-…/ # 최초 전환 시 기존 관리 파일·이력의 사본
│  └─ backups/library-….sqlite # 사용자가 요청한 로컬 이력 백업
├─ 작품 A/
│  ├─ project.json
│  ├─ episodes/*.md
│  ├─ doc/**/*.md
│  └─ assets/
└─ 작품 B/
```

문서 ID·제목·사용자 속성은 기존 Markdown 속성을 사용한다. 경로 변경은 ID를 기준으로 추적하며, ID가 없는 파일도 색인 과정에서 원고를 강제로 재작성하지 않는다. 중복 ID는 경고하고 원본들을 보존한다. 파일이 없는 상태와 읽지 못한 상태를 구분한다.

DB 유실 시 현재 원고는 파일에서 다시 읽을 수 있지만, 전환 후 쌓인 로컬 이력은 DB 백업이 있어야 복구할 수 있다. 색인 재생성과 이력 초기화는 별개 작업이다. 다른 폴더 동기화 프로그램으로 같은 서재를 공유한다면 `.lof/library.sqlite`와 WAL·SHM·잠금 파일을 제외해야 한다.

## 기기별 수정 이력

- 기존 이력 생성 간격·변경량 설정을 유지한다.
- 본문과 복원에 필요한 속성을 함께 압축하여 SQLite에 저장한다.
- 외부 편집과 원격 문서 반영으로 내용이 달라져도 이 기기가 마지막으로 관찰한 내용을 남긴다.
- 이력 복원은 현재 파일을 수정하는 작업이다. 복원 직전 원고도 보존한다.
- 문서를 삭제해도 로컬 이력을 즉시 지우지 않는다. 임시 원고는 기존처럼 정리한다.
- 하루 한 번 문서별 최근 100개·30일을 기준으로 정리하되 최소 10개를 보존한다. 정리 전 이력은 최초 이관 사본 또는 사용자가 만든 백업에 남아 있을 수 있다.
- 설정의 **로컬 이력 백업**은 SQLite 백업 API를 사용한다. 실행 중 DB 파일만 단독 복사하는 방식은 사용하지 않는다.

기기 A에서 수정한 뒤 B로 동기화하면 B에는 최신 문서가 전달된다. B가 교체 전 원고를 가지고 있었다면 그 내용은 B의 로컬 이력으로 남지만, A의 전체 수정 이력이 B로 전달되지는 않는다. 앱이 꺼져 있을 때 외부 편집기가 저장한 모든 중간 과정까지 기록하지는 못한다.

## 원본 파일 동기화 규격 files-v1

폴더·FTP/FTPS·WebDAV는 `lof-writer-files-v1` 아래에 동일한 서재 폴더 구조를 공유한다. 본문을 문서별 JSON으로 바꾸지 않는다.

```text
lof-writer-files-v1/
├─ .lof-sync-id               # 저장소 교체·유실 감지용 식별자
├─ 작품 A/
│  ├─ project.json            # 원본 작품 메타 정보
│  ├─ episodes/*.md           # 본문·YAML 속성 원본
│  ├─ doc/**/*.md
│  └─ assets/*                # 이미지와 첨부 파일 원본
└─ 공용 메모/                 # 서재 안에 있는 경우만 포함
```

- `.lof`, 숨김 경로, 임시 파일, `project.backup.json`은 전송하지 않는다. 관리 DB와 기기별 이력·잠금 파일은 각 기기에 남는다. `.lof/vault.json`의 서재 ID도 각 기기의 DB와 함께 유지한다.
- 파일 하나는 최대 50MB, 파일 경로는 최대 64단계, 목록은 최대 4만 파일로 제한한다. 심볼릭 링크·연결 폴더와 Windows에서 표현할 수 없는 경로는 거부한다.
- 마지막으로 양쪽에 반영한 파일별 SHA-256을 각 서재의 SQLite `file-sync-v1:<기기>:<연결>`에 기록한다. 원격 파일 목록과 로컬 파일을 비교하여 추가·수정·삭제를 반영한다. 본문 JSON 색인이나 DB 자체를 원격에 게시하지 않는다.
- WebDAV의 강한 ETag가 같으면 이전에 확인한 해시를 재사용한다. 신뢰할 수 있는 버전 정보가 없으면 원본 바이트를 읽어 해시를 비교한다. 변경되지 않은 파일은 다시 업로드하거나 로컬에 다시 쓰지 않는다.
- 충돌 사본 보관 모드에서는 해시 순서로 주 경로의 파일을 같게 선택하고, 다른 원본을 `.lof/file-conflicts/<해시>/<원래 경로>`에 보존한다. 최신 내용 모드에서는 수정 시각과 해시로 선택한다.
- 삭제와 편집이 겹치면 편집한 파일을 유지한다. 작품 전체 삭제와 그 작품의 다른 기기 편집이 겹친 경우 메타 정보를 포함해 작품을 보존한다. ID가 있는 문서의 이름 변경과 동시 편집이 겹치면 이전 경로의 수정본을 충돌 사본에 보관하고 새 경로를 유지한다.
- 원격 반영 전에 로컬 원고를 관찰해 기기별 이력을 남긴다. 전송 직전에 대상 파일의 해시를 다시 확인하며, 확인 중 변경되면 재시도한다. WebDAV 쓰기·삭제에는 가능한 경우 If-Match도 사용한다.
- 저장소의 `.lof-sync-lock` 폴더로 Writer 간 작업을 직렬화한다. 잠금 소유자를 확인하며 15초 간격으로 갱신하고, 5분 넘게 갱신되지 않은 잠금은 경로를 옮겨 회수한다. 초기 소유자 기록 전에 종료된 빈 잠금은 폴더 수정 시각을 기준으로 회수한다. 만료 잠금의 임시 파일은 격리 폴더에 보존한다.
- 저장소 식별자가 사라지거나 교체되면 대량 삭제로 해석하지 않고 동기화를 중단한다. 원래 경로를 복구하거나 연결을 다시 등록한다.
- 서재 밖에 별도로 지정한 공용 메모 디렉터리는 전송 대상이 아니다.

## 자동 동기화 시점

외부 저장소 설정과 README에는 동기화가 불안정할 수 있어 중요한 원고를 별도로 백업해야 한다는 안내, 모든 기기를 최신 버전으로 업데이트해야 동기화할 수 있다는 안내를 표시한다.

- 자동 저장과 작품·문서 변경은 설정한 파일 동기화 주기에 모아서 전송한다. 기본 5분이며 1분부터 1시간까지 지정한다. 수동 저장과 연결별 동기화 버튼은 즉시 실행한다.
- 파일 감시로 확인한 외부 편집도 동기화를 예약한다.
- 앱 시작·트레이 복귀·연결 추가 때 실행하며 트레이에서도 계속한다.
- 실패하면 30초 뒤 다시 시도한다. 수동 동기화 버튼도 유지한다.
- 다른 PC의 변경은 설정한 주기와 수동 동기화 때 확인한다.

외부 편집기의 임시 교체를 삭제로 오인하지 않도록 사라진 파일은 5초 이상 간격을 두고 재확인한다. 접근 오류·깨진 속성·불완전한 색인이 있으면 경고하고 안전하게 판단할 수 없는 삭제 및 동기화를 중단한다.

## 기존 사용자 마이그레이션

1. 기존 `.lof/vault.json`, `index.json`, `deleted.json`, 수정 이력, 연결별 동기화 상태를 읽는다.
2. `.lof/migrations/sqlite-v1-…/`에 바이트가 같은 사본을 만들고 대조한다. 원고와 작품 폴더는 이관 때문에 재작성하지 않는다.
3. 임시 `library.sqlite.migrating`에 색인·이력·기존 동기화 기준을 가져온다. 이력 본문·속성을 다시 읽어 대조하고 원본 변경 여부 및 DB 무결성을 확인한다.
4. 확인을 통과한 DB만 `library.sqlite`로 활성화한다. 이전 관리 파일과 이력 파일은 자동 삭제하지 않는다.
5. 전환에 실패하면 원본 파일 조회를 유지하고 DB가 필요한 편집·동기화는 중단한다. 읽을 수 없는 이력을 무시하고 정상 완료로 처리하지 않는다.

파일 저장 전에 이전 문서와 미완료 쓰기 기록을 남긴다. 저장 도중 종료되면 다음 실행에서 이전 문서를 로컬 이력에 보존하고 실제 파일 상태를 다시 읽는다. 미완료 기록을 근거로 현재 원고를 예전 내용으로 덮어쓰지 않는다.

현재 DB 스키마 버전은 1이다. 더 새로운 DB를 이전 앱이 임의로 초기화하지 않도록 버전을 확인한다. 최초 전환 사본은 전환 후 생긴 이력을 포함하지 않으므로 최신 백업과 구분한다.

## 기존 파일 동기화 연결 전환

`fileSyncResetGeneration`으로 일회성 전환을 관리한다. 완료 표시가 없는 설정에서 폴더·WebDAV·FTP 연결을 제거하고 완료 표시를 원자적으로 저장한다. 실제 연결을 제거한 사용자에게만 `fileSyncResetNoticePending`을 남겨 앱 시작 후 간단한 팝업으로 재연결을 안내한다. 안내 후 완료 상태를 저장한다. 저장 실패 시 다음 실행에서 다시 안내하며, 재등록한 연결은 이후 실행에서 유지한다. 원고·원격 파일·서재 경로·다른 앱 설정은 초기화하지 않는다.

## 구버전과의 호환

연결별 첫 동기화에서 기존 `lof-writer-sync-v1`의 기기별 스냅샷과 v2 색인을 읽어서 가져온다. 이후 구형 저장소에는 쓰거나 삭제하지 않는다. 새 파일은 `lof-writer-files-v1`에만 저장한다. 전환 완료 후 구버전에서 추가한 변경은 가져오지 않으므로 모든 PC를 먼저 업데이트해야 한다.

구버전 앱은 원본 파일 규격을 사용할 수 없다. 구버전으로 내리는 것은 새 SQLite 이력과 동기화 기준을 보존하는 복구 방법이 아니다.

## 확인 범위와 후속 작업

구현 코드에는 로컬 DB 전환, 이력 조회·복원 연결, 최신 항목별 전송, 외부 편집 예약, 백업을 반영했다. 빌드 검사는 기능의 실제 다중 기기 동작을 입증하지 않는다.

이전 SQLite 전환 당시 `npm run build`와 `cargo check`가 통과했다. 당시 기존 개발 앱 재시작 뒤 현재 서재의 원고 포함 파일 149개가 그대로인 것을 해시로 대조했고, SQLite의 이력·관찰 문서·본문 색인은 각각 145개였다. 최초 이관 사본 148개가 기록된 해시와 일치했으며 MCP 문서 목록도 145개, 경고 없음이었다. 테스트 스위트와 실제 원격 왕복 동기화는 실행하지 않았다.

- 실제 여러 PC의 동시 수정·오프라인 복귀·통신 중단과 각 저장소별 동작 확인.
- 다양한 기존 서재의 이관, 전원 중단 복구, 백업 복원 절차 확인.
- 필요 시 긴 문서 목록의 로컬 스캔 및 원격 요청 수 최적화.
- 삭제된 문서의 보존 이력을 문서 목록 밖에서도 탐색하는 화면.

테스트 실행과 배포본 생성은 사용자 요청에 따라 별도로 진행한다.
